# D.110c-0c1f5b0p alternatives report — is the retired-key Merkle AVL dictionary necessary?

Read-only analysis at branch `codex/phase3a1b-p6-golden-path` (HEAD e6a67013). No edits, no tests run. One `node -e` canonical-byte measurement was taken with `packages/canonical/dist`.

## Decisive recommendation

**Replace the Merkle AVL retired-author dictionary with a single creator-signed monotone `sequenceFloor` integer in the settlement checkpoint (candidate B). Every ACL addition — fresh or returning, no distinction — enters the active vector at `(sequenceFloor, sequenceFloor)`.** This is provably at least as safe as the dictionary for every property the dictionary was selected to provide, it is O(1) state with zero archive tier, it removes an entire store contract / IndexedDB schema / proof grammar / reachability GC / rollback-root machinery, it removes the "registry unavailable stalls membership-changing close" failure mode, and it shrinks the max-shape checkpoint from 7,064 to 6,959 bytes (measured). It costs one small `DurableIssuanceStore` method (`transactAdvanceLineage`) that the selected design *also* needs but never assigned an owner (finding P1-2 below).

The dictionary answers the question "what were this key's exact old boundaries?" The protocol does not need that answer. It needs only "is this key's new starting slot above every slot the creator ever accounted for it?" — and a global monotone floor answers that for every key at once without remembering any key. This is producer-epoch / ballot fencing applied to the sequence space.

**Conclusion.** The reducer, history, close set and charges are digest-keyed and anchor-fenced; a "sequence reset" cannot cause replay, double-apply or a wrong op in them. Lifetime `(author, seq)` monotonicity is consumed by exactly three things: (i) the creator's per-author frontier/terminal rule (which needs *monotone above every previously accounted slot*, not *exact continuation*), (ii) the author's own epoch-free issuance store, and (iii) the exported-but-unconsumed equivocation primitives. A reset **to zero** breaks (i) (a slot ≤ `settledThrough` is terminal, so a returning key restarting at 0 has all its new work declared terminal, or — worse — under v1 collides with accounted slots) and breaks (ii) on a stale device (`readIssued(scope, 0)` already holds the old row; a new row at seq ≤ watermark is classified as pruned). A jump **above the floor** breaks none of them.

### What v1 does today with a returning key (evidence for "what reset/continuation breaks")

`creator-close.ts:517-524`: for a successor writer with no prior boundary, `(sequences[0] ?? observedNext ?? 0) > 1` **throws** `D110C_0C1F1_AUTHOR_REENTRY_PROOF_REQUIRED` — for *any* author, not just the creator's. The close aborts; the vertex remains in the graph, so every retry aborts until the creator removes that author from the ACL. So under v1 today a returning writer that honestly continues its sequence (e.g. seq 57) blocks epoch rotation, and any fresh member that publishes first-seq ≥ 2 can block rotation until removed. The string is defined only in `creator-close.ts:71` and has no test (grep for `D110C_0C1F1_AUTHOR_REENTRY_PROOF_REQUIRED` hits only `src`/`dist`). This is a real per-room liveness hole in shipped v1 and is the concrete behaviour the settlement profile must replace. (P1-4.)

## 2. Candidates

Notation: `F` = `sequenceFloor` in the checkpoint; `H` = anchor `historySize` (RFC 9162 leaf count, authenticated in every anchor, `packages/protocol-v3/src/index.ts:460,735`).

### B. Global monotone `sequenceFloor` (recommended)

**Rule.** The checkpoint carries `sequenceFloor: number | null`. At settlement-profile genesis `F = null`. At each close, after the per-author scan over the *current* (pre-diff) ACL vector, `F' = max(F, every admittedThrough and settledThrough just signed, including those of members being removed)`. Every key in the successor ACL that is not in the current ACL enters the successor vector at `(F', F')` (or `(null, null)` iff `F' === null`). Removed keys are simply dropped. Nothing is remembered about them.

**Safety (proof).** Invariant I(k): for every key K and every slot s that any checkpoint C_j, j ≤ k, accounted for K (s ≤ boundary_j(K)), s ≤ F_k. Base: F_genesis = null, nothing accounted. Step: at close k the creator scans the pre-diff vector, obtaining boundary_k(K) for every current member; F_k ≥ all of them by construction and F_k ≥ F_{k-1} (monotone). A key added at close k starts at F_k ≥ F_j ≥ boundary_j(K) for every earlier j at which K was a member. So the added key's first accountable slot F_k + 1 is strictly above every slot the creator ever accounted for it, under any number of remove/re-add cycles. The creator's scan "advances from prior + 1 through exact adjacent accounted slots and never takes an observed maximum" is unchanged; it simply starts at F_k + 1. Therefore: no accounted slot is ever accounted twice; the terminal rule (rows ≤ settledThrough are terminal) covers every previously accounted row of a returning key; equivocation on an accounted slot remains impossible. This is exactly the property the dictionary was selected to provide ("re-added key … cannot reset"); the dictionary gives `=` old boundary, the floor gives `≥`.

**Adversarial.** A malicious added member that publishes at seq ≤ F: the vertex is a *new* digest under the current anchor and is applied once by the fold (same as today — ingress never checked sequences; the dictionary design does not change that either). Its frontier does not advance (regression for a foreign author freezes the boundary, `creator-close.ts:539-546` semantics retained). It cannot abort the close, cannot regress F, cannot affect another author. A malicious creator can already sign arbitrary boundaries under `creator-trusted-*`; the floor adds no new creator power.

**Liveness.** Close never waits on a store or proof; a membership-changing close is O(64) like any other. Per-author stall semantics unchanged. Fixes the v1 `AUTHOR_REENTRY_PROOF_REQUIRED` abort (P1-4).

**The author learns and jumps to the floor.** The settlement checkpoint is in the creator-signed transition closure every opener already authenticates. Under the settlement profile, before the first local issue after open/adopt, Node reads its own frontier `(a, s)` from the authenticated checkpoint and, if `lineage.next <= s`, executes one CAS `transactAdvanceLineage({scope, expectedLineage, next: s + 1})`. Local issue is refused until it commits. Rows with seq ≤ s in the local store are terminal (existing terminal rule) and are removed later by `pruneAuthenticatedSettledPrefix` after its gates; a pure `next` advance is consistent with the store's closure checks because gap ordinals have no rows and are never a terminal-readback candidate (`terminal.ts:107-124` only classifies the ordinal at `priorLineage.next`; `browser-issuance-store.ts:481-528` validates only existing rows). If `lineage.next > s + 1` (stale device that issued beyond the floor before removal), rows in `(s, next)` are ordinary displaced sources; the existing rebase drain dispositions them and the creator's adjacent scan from `s + 1` accounts them. No new path.

**What honest work is lost.** A removed-then-re-added key's rows that were issued before removal, never admitted, never dispositioned, and have seq ≤ F at re-add become terminal instead of remaining rebase-eligible. Assessment: ACL removal is an explicit creator authority decision that already blocks those rows for the whole removal period; re-admission is a creator-authorised fresh start above F. The author still holds the bytes; the application can re-submit the content as new operations. Nothing *accounted* is lost, and a fresh key loses nothing. The dictionary would keep those pre-removal pending rows rebase-eligible — that is the entire functional difference, and it is bought with O(R) archive state, a proof grammar and a strict-durability store.

**Interaction with `pruneAuthenticatedSettledPrefix`.** Unchanged contract; it already must handle a watermark jump across multiple epochs. Note it must accept `throughAuthorSequence >= lineage.next - 1` only after the advance CAS, because `lineage.next > watermark` is a store invariant (`maintenance.ts:147-158`, `closed-epoch-cleanup.ts:392-399`). The selected design has this same ordering requirement and does not state it.

**Rollback.** F regresses with the checkpoint; keys added in a rolled-back epoch are also outside the rolled-back ACL. Their rolled-back-epoch vertices were never accounted by any surviving checkpoint and cannot be admitted under any surviving anchor. Identical exposure to the dictionary (registry roots roll back too).

**Bytes.** Max-shape signed checkpoint (64 full frontiers, 256-code-unit object ID, safe-integer maxima) measured with the workspace canonical encoder: **6,959 B with `sequenceFloor` vs 7,064 B with `retiredAuthorRegistryRoot/Size`** (the 7,064 reproduces the design's own figure, so the comparison is like-for-like). Storage growth: **zero** (no archive tier, no rollback roots, no candidate root, no reclamation). Proof bytes: zero (vs ≤ 14,942,208 B worst-case batch witness in design f5b0p §"Proofs and deterministic updates").

**Owners/files that change vs. the selected design.**
- `packages/protocol-v3/src/creator-checkpoint.ts` (settlement checkpoint codec, per design §"Creator checkpoint and advancement"): replace `retiredAuthorRegistryRoot/Size` with `sequenceFloor`; validation: `sequenceFloor === null` iff no non-null boundary exists; every frontier boundary ≤ `sequenceFloor`; `sequenceFloor >= prior.sequenceFloor`.
- `packages/node/src/creator-close.ts` (settlement-profile scan, replacing lines 484-556 semantics for the new profile): compute F', seed added members at (F', F'). Delete the `AUTHOR_REENTRY_PROOF_REQUIRED` / "first observed must be ≤ 1" branch for the settlement profile (`creator-close.ts:517-536`).
- `packages/issuance-store/src/types.ts:84-91` + `conformance.ts`, `packages/storage-browser/src/internal/browser-issuance-store.ts`, `packages/storage-node/src/internal/node-issuance-store.ts`, in-memory model: add `transactAdvanceLineage`.
- `packages/node/src/v3-live.ts` open/adopt path (near `readLineage` use at 4812 and the barrier at 5973-6034): perform the advance before first issue under the settlement profile.
- **Deleted entirely**: f5b0p-a dictionary node/proof/transition codecs; f5b0p-b `RetiredAuthorRegistryStore` (memory + dedicated IndexedDB DB/schema), reachability GC, candidate/current/rollback root registration, ambiguous-commit recovery; the "registry census" line in the durable census; the `assert-absent` step; the "registry proof/store unavailable" failure row.
- Unchanged: vertex wire, signing domain, ACL schema (`latched-acl.ts`), settlement carrier grammar, terminal rule, profile-at-genesis boundary, compaction, live journal.

**Migration/compat.** Still a sibling genesis profile (`creator-trusted-settlement-v1`), because the checkpoint kind and terminal semantics are new — unchanged from the design. *Bonus:* late opt-in for existing `creator-trusted-v1` rooms becomes provable rather than impossible: every v1 admitted boundary is a dense prefix of graph vertices, each a history leaf, so `boundary ≤ H` for every key ever; setting `F = H` at the migration close dominates every boundary v1 ever signed for any key, removed or not, without a keyed index (the audit's stated reason for forbidding migration, audit §"Compatibility conclusion"). Keep this out of scope for f5b0 but record it as the migration owner's route.

**Browser feasibility.** Trivial: one integer, one IndexedDB CAS on an existing object store.

### A. Creator-computed floor derived from `historySize` (no new checkpoint field)

Bound: every accounted slot of any author is either a history leaf or one of ≤ 8 sources of a history-leaf control vertex, so `boundary ≤ 9·H` for every key. Seed added keys at `9·H`. Proof holds, but: (1) it bakes the carrier's source ceiling (8) into a safety bound — a derived constant that silently breaks if the ceiling changes (the project has already been bitten by derived-constant drift, see memory "Derived-constant adjacency sweep"); (2) `9·H` is far looser than B's exact `F`, so more of a returning author's pending rows are declared terminal; (3) it does not save the checkpoint field cost in any meaningful sense (B *removes* two fields and adds one). A is strictly dominated by B except as the v1→settlement migration floor (`F = H`, where v1 has no control vertices so the multiplier is 1). **Reject as primary; keep `F = H` as the migration derivation.**

### C. Incarnation-qualified identity `(pubkey, grantEpoch)`, sequence resets to 0 per incarnation

Which owners really change (from code, correcting the audit's list):
- **Wire/signing: no change is required.** The vertex already carries `epoch`/`anchor`; incarnations occupy disjoint epoch ranges, so a verifier holding the checkpoint can derive the incarnation of any vertex from its epoch. The audit's "changes never-resetting author identity across wire, signing" is overstated.
- **Issuance store: must change.** Lineage and `readIssued` are keyed `(objectId, author, seq)` with a monotone prune watermark (`browser-issuance-store.ts:355,411-416,444-465`; `terminal.ts:140-165`). Resetting to 0 on a stale device collides with retained rows and with `prunedThroughAuthorSequence` (a new row at seq ≤ watermark is "pruned"). The scope key would need the incarnation → new keyspace, new conformance, migration of `lineages`. Accurate.
- **Checkpoint frontier tuple and ACL grant: change** (incarnation ordinal in the tuple; grant record or derived grant epoch). Accurate.
- **Equivocation primitives: change** — `EquivocationScope` (`index.ts:1804-1808`) and the canonical proof record would need epoch/anchor, otherwise honest cross-incarnation vertices form valid proofs (`index.ts:4592-4660`). Accurate (latent).
- **Recovery classification: change** — `matches()` at `v3-live.ts:4602-4609` compares `(author, seq)` only; stale-device rows from a prior incarnation at the same seq would be misclassified.

So C is a real reset with real blast radius (issuance keyspace + checkpoint + proofs + recovery), and it buys nothing over B: B gives fresh sequence space without resetting anything. **Reject.**

### D. Creator-signed "fresh-key attestation" at grant

Circular without state: to attest freshness the creator must know the key never appeared, which is exactly the identity-history problem. The only non-circular attestation is "start above F" — which is B. **Reject as stated; B is its sound form.**

### E. Merkle AVL retired-key dictionary (baseline)

Safe (exact boundaries restored) but pays: O(R) reachable archive-tier nodes; a new proof/witness/transition grammar with deterministic rotations (f5b0p-a); a strict-durability content-addressed store with candidate/current/two-rollback root classes, ambiguous-commit recovery and reachability GC (f5b0p-b); a new failure mode where an unavailable node **stalls every membership-changing close**; ≤ 14.9 MB worst-case witness bytes; two extra checkpoint fields. Its exactness benefit — keeping a removed author's *unaccounted* pre-removal rows rebase-eligible after return — is small and only matters for stale devices. It also has the defects below (P1-1, P1-2) that B does not have.

## 3. Findings, ranked

**P1-1 — The selected design's two boundary-ordering rules contradict each other, and the dictionary insert would reject any author who ever had a dispositioned gap.** f5b0 design.md:367-368: "The admitted boundary … advances only across exact adjacent graph slots and never across a disposition." Settled advances across graph slots *or* dispositions (design.md:359-361). Both scans start at their own prior + 1 and both stop at the first slot that is not a graph vertex; only settled can cross it via a disposition; hence after the first disposition **settled > admitted** forever (example: slots 5 graph, 6 displaced+dispositioned, 7 graph → admitted 5, settled 7). But f5b0p design.md:55-56 requires "`settledThrough` may not exceed `admittedThrough`" for every registry node, and f5b0 design.md:395-396 defines the covered-historical range as "above `settledThrough` and at or below `admittedThrough`", which is then always empty. Consequence under E: removing such an author makes the `insert` mutation fail validation → the membership-changing close aborts before signature. Under B this contradiction is not load-bearing (added members get both boundaries equal), but the design text must still be corrected: either state `admittedThrough ≤ settledThrough` and redefine the covered-historical range, or drop `admittedThrough` from the settlement checkpoint entirely, since under the settlement profile every recovery decision is already determined by `settledThrough` (terminal) and "above settled" (displaced). Recommend dropping it: −64 integers from the max shape, one fewer monotonicity rule, one fewer thing for the floor to dominate.

**P1-2 — Neither design has an owner for the returning/fresh author's lineage jump.** f5b0p design.md:176: "its next authored sequence must be strictly above `admittedThrough`". `DurableIssuanceStore` (`packages/issuance-store/src/types.ts:84-91`) exposes `transactIssue`, `compareAndMarkOutboxPublished`, `readIssued`, `readOutboxPage`, `readLineage`, `close` — nothing advances `next`; `transactIssue` pins `authorSequence === prior.next` (`browser-issuance-store.ts:559-560`, `node-issuance-store.ts:600-601`); a missing lineage reads as `next: 0` (`browser-issuance-store.ts:413`). A fresh device for a returning author therefore issues at 0, which is ≤ settledThrough → terminal → its frontier never advances → its every future vertex is terminal on its own device. This is a liveness hole for that author in E and in B alike; B makes it explicit and assigns it (`transactAdvanceLineage`, f5b0d). The same method also closes the "existing member reopens on a fresh device" case for `next`.

**P1-3 — The dictionary adds a close-blocking availability dependency that the golden path forbids in spirit.** f5b0p design.md §"Store contract and custody": "If unavailable, that ACL-changing close stalls." The brief's golden path is a room alive for years with bounded reopen cost; ACL churn is the normal case in such a room, and the registry is the only component whose *absence* blocks a close. B has no such dependency.

**P1-4 — Shipped v1 liveness hole.** `creator-close.ts:517-524` throws `D110C_0C1F1_AUTHOR_REENTRY_PROOF_REQUIRED` for any prior-less successor writer whose first observed sequence in the close graph is > 1 (or whose local `next` is, for the creator). This aborts the close and keeps aborting until the author is removed. A returning honest writer or one malicious fresh writer (seq 2) blocks epoch rotation. No test references the constant. The settlement-profile scan must not inherit this branch; B's per-author freeze replaces it. v1 rooms remain affected until migrated (see B's `F = H` route).

**P2-1 — `admittedThrough` is redundant under the settlement profile** (see P1-1). If retained, the checkpoint validator must state the intended order explicitly and the dictionary/floor validators must use the same one.

**P2-2 — Exported equivocation primitives are epoch-agnostic** (`index.ts:1804-1808`, `4592-4660`) and have no production consumer. They are safe under B (no honest cross-epoch collision on accounted slots; unaccounted-slot collisions from a fresh device are possible in E and B alike). Note in the design that `EquivocationScope` must gain `anchor` before any production consumer is wired.

**P2-3 — "Lost local store of an active member" is unaddressed by both designs.** After a device loss, pending gap slots can never be dispositioned (no bytes to hash) and that author's settled boundary stalls forever. A `zero-intent`-style `unrecoverable` source kind (reference by `(epoch, anchor, seq)` only, permitted only when the creator can see the slot is absent from the current graph) would close it. Out of scope; record as debt.

**P3-1 — Permissionless rooms are fine.** `latched-acl.ts:336` still requires membership (`member !== undefined && (permissionless || writer)`), so every author is one of ≤ 64 members and the vector bound holds for B.

**P3-2 — `zero-intent`/join slots.** Under B a member added at epoch k issues its `join` at `F+1`; nothing outside pinned-genesis requires seq 0 (`v3-live.ts:4689,4711` are genesis-anchor-only; `4741,4781,6462` exclude seq 0 from covered-historical/displaced handling, which is consistent).

## 4. Replacement spec paragraph (drop-in for f5b0 design §"Creator checkpoint and advancement" and f5b0p)

> **Sequence floor.** The settlement checkpoint carries `sequenceFloor: number | null` in place of `retiredAuthorRegistryRoot` and `retiredAuthorRegistrySize`; no retired-author registry, store, proof or profile-specific archive tier exists. At settlement-profile genesis `sequenceFloor` is `null`. At every close the creator first runs the per-author admitted/settled scan over the complete **current** ACL vector (all current members, including any member absent from the successor ACL), then sets `sequenceFloor' = max(sequenceFloor, every non-null boundary just derived)`; `sequenceFloor'` is `null` only if `sequenceFloor` is `null` and no boundary is non-null. The successor frontier vector contains exactly the successor ACL's members: a member present in both ACLs carries its scanned boundaries; a member absent from the current ACL — whether or not that key ever appeared before, which the creator neither knows nor needs to know — enters at `(sequenceFloor', sequenceFloor')`. The checkpoint verifier rejects any record in which `sequenceFloor'` is below the predecessor's `sequenceFloor`, below any boundary in its own vector, or `null` while any boundary is non-null. Because every boundary the creator ever signed for any key is ≤ the floor at that close and the floor never regresses, a key's first accountable slot after any addition is strictly above every slot previously accounted for that key; the adjacent scan and the terminal rule are otherwise unchanged. Before its first local issue after open or adoption under this profile, Node reads its own frontier `(admittedThrough, settledThrough)` from the authenticated checkpoint and, when `readLineage(scope).next <= settledThrough`, executes `DurableIssuanceStore.transactAdvanceLineage({ scope, expectedLineage, next: settledThrough + 1 })` — a strict-durability CAS that only moves `next` forward and never touches rows or the pruned watermark; local issue is refused until it commits or the outcome is authenticated on reopen. Rows at or below `settledThrough` remain terminal and are reclaimed only through `pruneAuthenticatedSettledPrefix` after its existing gates; rows above it that already exist locally are ordinary displaced sources. Unpublished, unaccounted rows of a removed key whose sequence is at or below the floor at re-admission are terminal; re-admission is a creator-authorised fresh start, and the application may resubmit their content as new operations.

**Failure/adversarial matrix rows changed** (f5b0 design §"Crash, attack and failure matrix"):

| Boundary or attack | Required result (replacement) |
|---|---|
| same-key removal/re-entry | member enters at `(floor, floor)`; every previously accounted slot is ≤ `settledThrough` and terminal; no fresh/returning distinction is made or needed |
| genuinely fresh key | enters at `(floor, floor)`; sequence zero is accepted only while `sequenceFloor === null` (genesis) |
| ~~registry proof/store unavailable~~ | row deleted — no store exists; membership-changing close never waits on storage |
| added member's first sequence ≤ floor | vertex is ordinary current-anchor application evidence; that author's boundaries do not advance; close proceeds |
| `sequenceFloor` regresses, is `null` with non-null boundaries, or is below any vector boundary | checkpoint rejected at verify/open |
| author local `next` ≤ own `settledThrough` after open/adopt | Node advances lineage by CAS before first issue; issue refused until commit; ambiguous outcome resolved by reopen readback |
| author local `next` > own `settledThrough + 1` | rows in between are displaced sources; existing disposition path; boundary advances only adjacently |
| rollback to a prior checkpoint | floor regresses with the checkpoint; keys added in rolled-back epochs are outside the rolled-back ACL; unaccounted rows stay unaccounted |
| creator omits a removed member from the max | unrepresentable in verification (creator-trusted profile); RED must drive removal-then-re-add and assert the re-added boundary ≥ the removed member's last signed boundary |

**TDD slice changes.** Delete f5b0p-a and f5b0p-b. f5b0a adds `sequenceFloor` codec/validation. f5b0d adds `transactAdvanceLineage` (memory/browser/node + conformance) alongside `pruneAuthenticatedSettledPrefix`. f5b's causal RED replaces "registry membership restores exact boundary" with: create settlement-profile room; author issues/settles to boundary b; remove; ≥ 2 closes with other activity raising the floor; re-add; assert vector entry ≥ b, first honest issue at floor + 1 advances, a forced issue at b + 1 does not advance and does not abort the close; a genuinely fresh key added in the same epoch also enters at the same floor. Retain the ≥ 100-transition remove/re-add churn gate; its census no longer contains a registry line.

## 5. Prior art, briefly

The floor is Kafka's producer-epoch fencing and Paxos/Raft ballot/term fencing applied to the sequence space: a re-registered producer gets a strictly larger epoch and brokers refuse lower ones; nothing about the old producer is remembered. MLS (RFC 9420) reuses leaf indices safely because the epoch is in the key schedule and old epochs are deleted — the analogue is this protocol's anchor fencing at ingress, which is already why the reducer never needed lifetime uniqueness. Automerge/Yjs's "never reuse an actor ID" is the incarnation route (C) and is unnecessary here because the sequence space, not the identity, is what needs to be fresh. Keybase per-user-per-team generations are C with explicit counters — same blast radius as C.
