# Golden-path gap report — D.110c author settlement vs. the real code

Anchor inspected: HEAD `e6a67013` on `codex/phase3a1b-p6-golden-path` (read-only; no tests run).
Design docs: `.logs/d110c-0c1f5b0-design-00a860ab/design.md` (f5b0), `.logs/d110c-0c1f5b0p-design-e6a67013/{design,audit}.md` (f5b0p), `.logs/d110c-0c1f5b0-plan-review-fc4b8fc7/review.md`.

Claim under test: a `creator-trusted-settlement-v1` room rotates 0→1→…→100+ with (a) bounded control state, (b) age-independent cold reopen, (c) no honest op lost, (d) same-key remove/re-add safe.

**Verdict.** The settlement design closes the *authority* gap (why the creator may advance a frontier across a displaced slot), and it is internally sound for (a) at the checkpoint level and for (c)/(d). It does **not** deliver the golden path on its own, because three things it assumes are not in the code today and are not owned by any of the seven slices: (1) physical pruning/reclamation is not wired into any production path, so cold reopen is already O(lifetime rows) and already *fails* once an author's covered rows exceed `maxEpochVertices`; (2) non-creator peers have no hot-follow path — every non-creator epoch transition is a cold reopen with an out-of-band declaration; (3) several durable stores (live-journal old scopes, snapshot-transfer scopes, seal evidence) and one in-session map grow with epoch/op count and have no deletion owner. Two design-internal defects also need fixing before RED (admitted/settled inequality is inverted between the two design documents; the honest delivery-gap row is *published*, and the current rebase scan only yields *pending* rows).

## 3. The ≥100-transition gate

- There is **no** such test. `tests/` has no transition-count constant; no test goes past epoch 3.
- The gate is defined as D.110c-d (plan :92058-92070): tests-only, after D.110c-a/b/c GREEN; one room, ≥100 genuine close/adopt calls, no adaptive retry, durable census of the four seal stores + freshness floor + Node control owners, state-bytes equality at each boundary. D.110c-0b1 promises the bound "for at least 100 genuine same-room" transitions (plan :93278). The f5b0p design adds remove/re-add, restarts before/after registry commit, prune boundaries, registry census and a "fresh-process post-GC memory gate" (f5b0p design §Bounds).
- What it would prove today (if D.110c-c were done): creator-side rotation, closure boundedness, snapshot/state agreement.
- What f5b must add: per-author settled/admitted advancement across ≥2 closes, terminal recovery, gated prune, restart/cold reopen — *including a non-creator writer* (the plan at :97187 asks for "cold reopen as the non-creator writer"). Because of G5 the non-creator half of the gate is reopen-per-epoch and therefore also measures G2 directly.
- The memory gate is fresh-process; G9 (in-session growth) needs an additional long-lived-session sampling to be meaningful.

## 5. Design defects found against the code (must fix before RED)

**D1 (P1) — admitted/settled inequality is inverted between the two documents.** f5b0 says `admittedThrough` "advances only across exact adjacent graph slots and never across a disposition" (l.367-368) while `settledThrough` advances across dispositions (l.377-381). After any gap, settled > admitted (in the walk-through: settled 13, admitted 9). The f5b0p node grammar requires "`settledThrough` may not exceed `admittedThrough`" (f5b0p design l.55-56). Under that rule, removing Alice after a settled gap would require inserting `{admitted: 9, settled: 13}` → invalid node → every membership-changing close fails closed. Also f5b0p's re-add rule "its next authored sequence must be strictly above `admittedThrough`" (l.175-176) should be `settledThrough`: with admitted 9, a re-added Alice could author sequences 10–13, which are terminal — ingress admits them, the creator scan sees a same-slot conflict and stalls her. Fix: invert to `admittedThrough ≤ settledThrough` and key the re-add floor on `settledThrough`. Consider dropping `admittedThrough` from the settlement checkpoint entirely; after the first disposition it is a permanently stale number whose only consumer (`covered-historical`, l.396-397) becomes vacuous.

**D2 (P1) — hidden scope in f5b0b/f5b0c: the honest delivery-gap source is a *published* row.** `readRebaseOutbox` yields only pending displaced rows (`v3-live.ts:6446`) and skips published historical rows (:6445). The design's own second trigger (row 11) is published. "Rows above the authenticated settled frontier are drained" (l.273-275) requires replacing the pending filter with "above `settledThrough`" and admitting published rows into the disposition loop; no slice names this change, and the room-side `already-present` path (l.278-280) is otherwise unreachable for exactly the case the plan calls out (:98680-98688). Without it the frontier stalls exactly as today.

**D3 (P2) — ingress has no per-author sequence floor.** No code enforces a minimum author sequence at admission (no floor/regression check in `v3-live.ts`; the f5b audit notes admission does not require adjacency). The design places "next sequence strictly above the restored boundary" in the ACL transition law (f5b0p l.175-176) but names no admission owner. The creator scan will treat a slot ≤ settled as "same-slot equivocation → stall" (l.360-365), which is fail-closed but means a re-added honest client that restarted its lineage below the boundary is silently stalled forever and burns epoch capacity. Name the owner (f5b0b admission, reading the current checkpoint) or state explicitly that it is deferred.

**D4 (P2) — control-vertex capacity from non-writers.** Admission requires only ACL membership (l.196-204). A member with no write role can author an unbounded chain of `settlement-control` supersessions and `zero-intent` sources, each ≤ 8,192 B, consuming `maxEpochVertices`/`maxEpochBytes` for the epoch. Cap controls per author per epoch (one outstanding + supersede) or require the writer role.

**D5 (P2) — "No state grows with epoch count" (l.426-427) is true only for the checkpoint.** It is false for the product until G1/G2/G5/G6/G7/G9/G10 have owners; the acceptance text (l.586-588) should cite D.110c-c/d as the owners instead of implying f5b delivers the census.

## 6. Slice ordering and hidden scope

Dependency check of the 7 slices as written: f5b0p-a → f5b0p-b → f5b0a → f5b0b → f5b0c → f5b0d → f5b is *correct* but front-loads the two dictionary slices, which the golden path needs only for remove/re-add, and leaves the prune *invocation* (D.110c-c) outside the list.

Most likely to explode: **f5b0b**. It touches `v3-live.ts` (8,082 lines): six `preparedBlueprintAdmission` families (l.218-224), `classifyPlaneVertex`, `creatorFilteredIssuanceStore`, the replay loop, `readRebaseOutbox`, the close-map split into application ⊔ settlement while keeping charges/history/close-set on the union, plus restart enumeration of outbox + live journal before authoring (l.263-267). Second: **f5b** — it must fork `creator-close.ts:470-583` and `creator-transition-advance.ts:302-541` into a profile-selected parallel path while keeping v1 byte-identical. Third: **f5b0p-b** (new IDB schema with CAS, candidate/current/rollback root classes, poison semantics, reachability GC).

**Can the dictionary be deferred?** Yes, and consistently with the design's own text. The design already says "Same-key removal/re-entry remains fail closed pending the separately named bounded identity-history prerequisite" (l.183-185). The correct fail-closed point is **full removal, not re-grant**: without the registry the creator cannot tell a fresh key from a returning one, but if no key has ever been fully removed (i.e. creator close refuses any ACL transition whose `freezeMembers()` result drops a key, `latched-acl.ts:351-368`), then "absent from the prior frontier vector" ⇔ "never appeared", and the f5b0p law degenerates exactly to: every add is `assert-absent` on the empty root. Ship the checkpoint with `retiredAuthorRegistryRoot = empty root` (already defined, f5b0p l.22-23) and `retiredAuthorRegistrySize = 0` from f5b0a onward; rooms created in the interim need no migration when f5b0p lands because their registry is legitimately empty. Cost: lifetime distinct members ≤ 64 until f5b0p; removal of a member is refused (the interim room can only demote roles, which retains the frontier per l.335-337). This is an ordering change with a fail-closed guard, not a "nearby substitute" (stop rule l.573-579).

Recommended critical path (each with its causal RED):

1. **f5b0a** — carrier + checkpoint codecs, profile union, registry fields fixed to empty root/0, global action reservation. Fix D1 in the checkpoint grammar first.
2. **f5b0b** — Node admission, close split, settlement transaction, terminal-row skip, restart enumeration. Include the `readRebaseOutbox` widening (D2) here because the scan lives in `v3-live.ts`.
3. **f5b0c** — room dispositions incl. `already-present` on published rows, `zero-intent`, manual-review hold; `hasDisplacedOperation`.
4. **f5b-core** — creator settlement scan + checkpoint emission under the settlement profile, terminal recovery, fail-closed removal guard, empty registry. RED: the §4 scenario through 3 closes + restart + cold reopen for creator *and* non-creator (via reopen-with-declaration, since G5). This is the first demonstrable repeated-epoch rotation with displaced ops.
5. **f5b0d + D.110c-c wiring** — `pruneAuthenticatedSettledPrefix` **and** its production invocation on every peer after adoption/rollback gates; raise or re-base the `countHistoricalIssuanceRow` cap (G2); AHE reclaim + journal/snapshot/seal scope retirement (G6-G8, G10). Only after this can (a)/(b) be measured.
6. **D.110c-d (no-re-add variant)** — ≥100 transitions, both creator and one non-creator writer, census incl. issuance/journal/snapshot/seal rows.
7. **f5b0p-a, f5b0p-b, f5b-registry** — lift the removal guard; extend the gate with remove/re-add, restart before/after registry commit.
8. **Phase 7 / G5 / G14** — non-creator hot follow, archive segmentation, cold join.

## 7. Top 5 risks

1. **Boundedness is unverifiable and cold reopen already fails with age (G1/G2).** Nothing calls prune/cleanup/reclaim in production; the recovery scan is O(lifetime rows) with a hard `maxEpochVertices` cap on covered rows that the design's rollback-gated prune does not keep under (up to ~3 epochs of rows resident). Owner missing from the slice list.
2. **f5b0b blast radius in `v3-live.ts`.** Six admission families, filtered stores and the replay loop must gain a settlement branch without changing v1 bytes; the pending-only rebase filter must change (D2). High probability of a RED that contradicts the matrix and forces the reslice the design itself mandates (l.566-568).
3. **Design-internal contradiction D1.** If f5b0p RED pins `settled ≤ admitted` and f5b RED pins settled advancing across dispositions, the first membership-changing close after any gap fails closed. Fix the inequality and the re-add floor before any RED; decide whether `admittedThrough` survives at all.
4. **Non-creator peers reopen every epoch (G5).** The golden path for a non-creator author is 100 cold reopens, so risks 1 and 2 are paid per peer per epoch; the D.110c-d gate as defined is creator-side only and will overstate readiness unless a non-creator writer is included.
5. **Growth outside the checkpoint (G6/G7/G9/G10).** Live-journal old scopes retain every accepted vertex of every epoch, snapshot scopes retain every epoch's snapshot, and the room session map is never cleared; the design's "no state grows with epoch count" claim (l.426-427) will be falsified by the census D.110c-c is required to produce, and the fresh-process memory gate cannot see G9.

Answers to the brief's residual questions, briefly: a single absent author cannot block rotation (f5a made close anomalies author-local, `creator-close.ts:489-535`; the design keeps that at l.380-381) — she only stalls her own frontier and, today, bricks her own node (G4). A malicious member cannot abort close but can exhaust epoch capacity with control vertices (D4). "Sequence reset" would break: issuance lineage monotonicity and the pruned watermark (`issuance-store/src/maintenance.ts:157`; `browser-issuance-store.ts:445-447` latches corruption for a consumed address above the watermark), the dense-prefix scans in `creator-close.ts:539-547` and `closed-epoch-cleanup.ts:404-435`, covered-historical classification (`v3-live.ts:4756`), and equivocation-by-slot detection in the creator scan — all of which key on lifetime-unique `(author, sequence)`; the design is right to keep never-resetting sequences and add the registry rather than incarnations.
